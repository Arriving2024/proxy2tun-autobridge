# 现场调试记录与证据边界

更新日期：2026-10-31。整理目标为实验性 v0.2.1。记录用于解释修复与回归用例，不表示该版本已经在所有记录涉及的电脑上部署成功。

仅保留故障分类、公开探测站点和脱敏观察。示例路径、回环地址及配置排除范围不是设备网络快照；不附原始日志、Cookie、账户、节点、订阅、请求标识或会话标识。

## 如何阅读证据

| 标记 | 含义 |
| --- | --- |
| 原始输出 | 可见的用户粘贴终端结果；仅支持其中直接显示的事实 |
| 本机验证 | 维护者在本次设备上实际执行、观察并复核的结果 |
| 代码确认 | 在对应源码中能直接确认的行为；不等于完成了实机验收 |
| 回顾 / 建议 | 历史助手总结、第三方评价或未执行方案；不能补写成原始实测 |

## 朋友电脑部署：代理可达，TUN 未运行

来源为聊天《部署Proxy2TUN AutoBridge》中目前可读取的用户输出。接口没有提供更早轮次的可用游标，因此不能补齐助手回顾所引用的全部原始终端记录。

聊天描述使用 v0.2.0，安装目录为 `%LOCALAPPDATA%\Proxy2TUN-AutoBridge`；代理客户端位于含中文名称的非系统盘目录。本文使用 `D:\示例程序\ProxyClient\ProxyClient.exe` 表示这类路径，不保留个人目录。调试先使用原 Watch 入口，后改用管理员终端直接运行已生成的 `runtime\preview.json`。

| 观察 | 证据 | 能支持的结论与限制 |
| --- | --- | --- |
| Misty 与其 v2ray 核心存在，sing-box 和 `p2t-*` 网卡未出现 | 原始输出 | 原代理已启动，但该时刻没有 TUN 接管；不能把“客户端进程存在”当作全局代理正常 |
| 显式 `socks5h` 请求 OpenAI API 返回 HTTP 401 | 原始输出 | 该代理链路完成 HTTPS 并得到服务端响应；未携带认证信息，不代表账户或模型调用成功 |
| 手动运行已有 preview 后，`p2t-*` 网卡为 Up，未指定显式代理的 API 请求返回 `Missing bearer authentication` | 原始输出 | 支持当次 TUN 存活及系统请求获得 API 响应；可见轮次没有用户确认 ChatGPT 实际发送消息成功 |
| 原 Watch 出现 `TunRoutesNotReady`、回滚；指定代理的 Generate 耗时约 52.07 秒 | 回顾 | 这些数值和报错来自助手回顾，当前可见页面没有对应的原始测量输出，不能作为新版本基准结果 |
| 绕过 Watch 后应用流量进入 TUN / SOCKS | 回顾，部分传输结果有原始输出支持 | 是排查线索；不能据此证明 Watch 生命周期、退出清理和自动恢复已经通过 |
| 一键启动 Misty、后台运行 TUN、退出客户端后联动停止的计划任务安装器 | 建议 | 历史回复明确说明尚未在朋友电脑实测；本项目不把它写成已落地能力，也不自动执行或安装该历史方案 |

### 能独立确认的封装缺陷

v0.2.0 代码中的两个问题不依赖于上述历史耗时数字：

- `ProxyEndpoint` 已明确时，代理发现仍经过全量监听发现路径。v0.2.1 已改为只检查指定入口，同时保留协议、转发和进程归属核验。本机新版 Generate 约 3.92 秒并通过核心校验；与朋友历史耗时不是同条件比较。
- 配置会排除 IPv4 / IPv6 回环范围，Windows 可能因此生成多段路由。旧健康检查仅接受默认路由或两条 `/1`，无法接受这种完整布局。已用合成布局先重现旧检查失败，新检查改为按实际前缀的严格并集验证除回环外的目标范围，仍拒绝缺口、错误网卡身份和残缺地址族。

对应测试要覆盖含中文的安装/客户端路径、明确入口下不扫描无关端口、真实生成配置的拆分覆盖，以及删除任意必要覆盖段后的拒绝行为。

### 诊断命令本身也可能出错

一段 Windows PowerShell 原始输出中，手动 curl 命令包含 `--proxy "" --connect-timeout 5`，随后错误目标却成为 `0.0.0.5:80`。这是原生空参数丢失、后续参数错位的强烈线索，**不是 DNS 已损坏的直接证据**。没有在朋友电脑独立复现参数传递，因此保留为推断。

微软说明 PowerShell 7.3 的原生参数传递行为与 Windows PowerShell 5.1 不同，新行为才保留这类空字符串参数。排查时使用项目的有界进程封装，具体步骤见[故障排查](troubleshooting.md#使用项目内置检查区分-dns-与-https)，不要反复复制存在歧义的命令。[微软参数说明](https://learn.microsoft.com/en-us/powershell/module/microsoft.powershell.core/about/about_parsing?view=powershell-7.6)

## 2026-10-30 本机：监测器误判两种有效状态

以下发生在保留原配置的本机 legacy 启动器中。修复内容可以作为通用版本的回归依据，但该启动器不是 v0.2.1 的完整通用 Watch 封装。

| 观察与修复 | 证据 | 发布时应保留的约束 |
| --- | --- | --- |
| Windows 监听表出现 PID 0、重复条目或过滤漏项；直接建立回环连接及 SOCKS5h HTTPS 均可用 | 本机验证 | 监听元数据异常不能直接解释为端口关闭；PID 0 不能映射成 Idle 后误报绕过配置错误 |
| 保持自己的 TCP 连接，查询 Established 表，再按服务端完整四元组核验真实所有者，成功识别代理核心 | 本机验证 | 只接受唯一正 PID 和可核验的实际进程；未知或冲突时拒绝启动，不能凭同名进程存在或 HTTPS 成功推断端口归属 |
| 随机自造测试域名返回 `NOERROR`、零 Answer 和 authority SOA，旧解析器判为无效 | 本机验证及真实报文回归 | 合法 NODATA 是 DNS 负回答，不等于解析通道故障；不得因此停掉健康 TUN |
| 修复后接受覆盖查询名的 IN/SOA 负回答，继续拒绝错误事务、问题、类、截断、无关 SOA、空回应和 SERVFAIL | 代码与回归测试 | 不以接受任意空 DNS 报文换取“健康”；保留来源与完整结构核验 |
| 修正后的本机 legacy 启动器连续五轮 DNS / HTTPS 检查通过，HTTPS 为 204；原配置完整性保持不变 | 本机验证 | 只证明该设备、该旧配置和该启动器的此次运行；不等于朋友电脑、新版安装/Watch/回退已经通过 |

NODATA 的判定依据见 [RFC 2308 §2.2](https://www.rfc-editor.org/rfc/rfc2308.html#section-2.2)。回归用例只使用自行生成的问题与公开 DNS 数据，不收录用户浏览流量。

## 新版本应如何验收

可移植的是明确入口快速发现、可靠进程归属核验、拆分路由覆盖、NODATA 解析及其测试。不要把某个客户端的固定路径、端口或后台计划任务复制成通用默认值。

通用包仍采用前台运行、有限重试和退避、配置备份/回滚及归属核验停止；默认不创建开机任务。达到恢复上限后应暂停并给出可解释诊断，而不是隐藏无限重建。

发布前后分别记录：源码实现、当前提交自动化检查、指定构建的真实管理员验收，以及真实应用操作。完整通用封装尚未验收的项目继续保留在[验证清单](validation.md)中；实验性发布不能替代这些结果。
